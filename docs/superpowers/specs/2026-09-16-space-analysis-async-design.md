# Анализ пространства: асинхронный режим — дизайн

Дата: 2026-09-16. Статус: одобрено в чате, реализуется. Развивает
`2026-09-16-space-analysis-design.md`: та же модель, промпт, лимиты и доска-анализ,
меняется только то, как задача запускается и как о ней узнают люди.

## Зачем

В первой версии клик держал HTTP-запрос до ответа модели и в конце принудительно
переводил на новую доску. Пользователь в это время мог работать, и его выдёргивало;
другие участники пространства вообще не знали, что идёт анализ. Нужен полный
асинхрон: клик только запускает задачу, все в пространстве видят плитку-заглушку
с лоадером, по готовности всем приходит уведомление, переходов нет, и ничего не
зависит от того, на какой странице человек находится.

## Решения (зафиксированы с пользователем)

- **Никаких редиректов.** По готовности всем в пространстве всплывает уведомление
  «AI-анализ готов» с кнопкой «Открыть».
- **Лоадер видят все.** Плитка «Анализ пространства за d.m.Y» с лоадером появляется
  в списке досок у всех, кто в пространстве, сразу после клика любого участника.
  Пока анализ идёт, в плитку перейти нельзя. Потом это обычная доска-анализ.
- **«Анализ запущен» тоже видят все**, не только нажавший.
- **Ошибки — уведомления в правом верхнем углу** в стиле сайта. Плюс плитка
  «Анализ не удался» с причиной и кнопкой «Повторить», чтобы состояние пережило
  перезагрузку.
- **Всё состояние в базе**, живые обновления через Socket.IO, а не поллинг.

## Хранение: таблица `space_analyses`

Незавершённый или упавший анализ — не доска, поэтому доска по-прежнему создаётся
только при успехе. Состояние живёт в новой таблице (миграция `0006_space_analyses.sql`,
руками, как остальные):

| колонка | тип | смысл |
|---|---|---|
| `id` | uuid pk | |
| `space_id` | uuid → spaces, cascade | |
| `state` | text: `pending` / `ready` / `failed` | |
| `error` | text null | вид ошибки для failed |
| `title` | text | «Анализ пространства за 16.09.2026», по локали нажавшего |
| `locale` | text | `en` / `ru` |
| `board_slug` | text | slug будущей доски, генерируется при старте |
| `creator_token` | text | токен будущей доски, чтобы нажавший сразу получил cookie |
| `board_id` | uuid null → boards, set null | заполняется при готовности |
| `created_at` | timestamptz | |
| `finished_at` | timestamptz null | |

Выводы из таблицы (чистые функции в `src/lib/server/analysis.ts`):

- **Живой pending** — запись `pending` моложе 5 минут (`PENDING_STALE_MS`). Старше —
  рестарт сервера посреди работы; такая запись считается `failed` с ошибкой `timeout`.
- **Последний ready** — самая новая запись `ready`, у которой `board_id` не null
  (доску могли удалить). Кеш актуален, если она новее последней обычной доски.
- **Показываемый failed** — самая новая запись, если она failed (или устаревший
  pending) и нет более новой ready или живой pending.
- **Лимит** — записи ready и живой pending за последние 24 часа, три и больше —
  отказ. Failed не считаются.
- Перед стартом новой попытки failed-записи пространства удаляются.

## Фоновая задача и события

Form action `analyze` (`POST /spaces/{slug}?/analyze`, поле `locale`):

1. Доступ к пространству как раньше (пароль введён, пароля нет или создатель).
2. Ключа нет → `fail(503, { analysis: 'not_configured' })`.
3. Живой pending есть → `fail(409, { analysis: 'running' })`.
4. Кеш актуален → `{ analysis: 'cached', boardSlug }` (уведомление «Анализ
   актуален» с кнопкой «Открыть», без перехода).
5. Лимит → `fail(429, { analysis: 'limit', retryInHours })`.
6. Карточек нет → `fail(400, { analysis: 'no_cards' })`.
7. Удалить failed, вставить pending с заголовком, slug и токеном, поставить cookie
   `retro_creator_{boardSlug}` нажавшему, послать в шину `analysis:state`
   (pending), **запустить задачу без ожидания**, ответить `{ analysis: 'started' }`.

Задача `runAnalysisJob(rowId)`: DeepSeek → разбор → транзакция «доска +
карточки» (slug и токен из записи) → запись `ready`, `board_id`, `finished_at` →
шина `analysis:state` (ready, с `board: { slug, title }`). Любая ошибка → запись
`failed` с видом ошибки → шина `analysis:state` (failed). Виды ошибок те же:
`network | timeout | http | bad_response | empty`. Метрики и логи как раньше.
Замок `runOnce` больше не нужен: его роль играет живой pending в базе.

**Шина.** `server.js` создаёт `globalThis.__retroBus = new EventEmitter()` до
загрузки SvelteKit-хендлера и подписывается: событие `space` `{ spaceSlug, event,
payload }` → `io.to('space:' + spaceSlug).emit(event, payload)`. SvelteKit-сторона
(`src/lib/server/bus.ts`) кидает в шину, если она есть; в `npm run dev` шины нет,
события молча теряются. Один процесс, поэтому этого достаточно.

**Состояние по HTTP.** `GET /spaces/{slug}/analysis` (`+server.ts`) отдаёт текущее
состояние тем же правилом доступа, что и пространство. Клиент дёргает его один
раз после `space:join`, чтобы не проиграть гонку «задача закончилась, пока сокет
подключался», и после реконнекта.

Payload `analysis:state` и ответ endpoint'а:

```ts
{ state: 'idle' }
| { state: 'pending', id, title, createdAt }
| { state: 'ready',   id, title, createdAt, board: { slug, title } }
| { state: 'failed',  id, title, createdAt, error }
```

## Сокет-комната пространства

- Клиент шлёт `space:join { slug }` со страницы пространства и со страниц досок
  внутри пространства (в дополнение к `board:join`). Сервер выводит сокет из
  прежней комнаты пространства и заводит в `space:{slug}`; проверок доступа нет —
  в комнате нет содержимого, только статус анализа, а slug пространства и так
  неугадываем.
- Стор сокета держит `analysis` (payload выше) и применяет переходы:
  первое применение (после загрузки страницы или fetch после join) — молча;
  переход в pending — уведомление «Анализ запущен»; в ready — «AI-анализ готов»
  с кнопкой «Открыть»; в failed — уведомление с текстом ошибки. Одинаковое
  состояние с тем же `id` повторно не уведомляет.
- Страница пространства при ready делает `invalidateAll()`, чтобы доска-анализ
  появилась в списке со счётчиками; плитка-заглушка держится, пока доска не
  появится в данных.

## Интерфейс

- **Уведомления.** Стор `toastStore` и компонент `Toasts.svelte` в layout: правый
  верхний угол, стопка сверху вниз, карточка в стиле сайта (скругление 16px,
  рамка, `surface-card`, тень), слева иконка по типу (info / success / error),
  текст, необязательная кнопка-ссылка действия, крестик. Авто-скрытие 8 секунд,
  ошибки 12. Переживают переходы между страницами, потому что живут в layout.
  Все статусы анализа идут через них; плашка снизу из первой версии убирается.
- **Кнопка «Анализ пространства».** Ответ сервера приходит быстро (задача уже в
  фоне). Локальные результаты действия: `cached` → уведомление «Анализ актуален» с
  «Открыть»; `running` → «Анализ уже идёт»; остальные ошибки → уведомление с
  текстом. `started` ничего не показывает: «Анализ запущен» придёт всем по сокету,
  включая нажавшего.
- **Плитка-заглушка** (в `SpaceBoardGrid`, первая после «Новая доска»): градиентная
  рамка, заголовок из записи, спиннер и бейдж «Анализ…», `div`, не ссылка,
  `aria-busy`. Failed: та же рамка, приглушённая, заголовок, строка «Не удалось:
  причина», кнопка «Повторить» (та же форма action). Ready: плитки-заглушки нет,
  доска в общем списке как обычно.
- **Страницы досок внутри пространства**: плитки нет, уведомления приходят.
- Кнопка по-прежнему только при заданном ключе.

## Тесты

Юнит (`analysis.test.ts`): живой/устаревший pending, последний ready без доски
игнорируется, показываемый failed, лимит поверх записей, полезная нагрузка
`statePayload` для каждого состояния, `emitSpace` без шины не падает, переходы
уведомлений в сторе (первое применение молчит, повтор не дублирует).

E2e (`analysis.spec.ts`, переписывается): мок получает задержку
(`POST /__mode { mode, delayMs }`). Сценарии:
1. Клик → у нажавшего и у второго браузера в пространстве появляется плитка с
   лоадером и уведомление «запущен»; по готовности у обоих уведомление «готов»,
   плитка становится доской; переход только по кнопке «Открыть».
2. Нажавший в момент готовности на странице доски внутри пространства — получает
   уведомление там, без перехода.
3. Перезагрузка во время анализа показывает лоадер снова.
4. Ошибка мока → плитка «не удалось» с «Повторить» у обоих, уведомление об
   ошибке; повтор в режиме ok доводит до доски.
5. Кеш: повторный клик без новых досок → «Анализ актуален» с «Открыть», новых
   записей нет.
6. Лимит: четвёртая попытка за сутки → уведомление о лимите.
7. Пустое пространство → «нечего анализировать».
8. Админ пространства видит меню создателя на готовой доске; одиночная доска без
   кнопки; на телефоне доска-анализ открывается на первой колонке.

## Вне рамок

Поллинг как запасной канал, история анализов в интерфейсе, отмена идущего
анализа, очередь задач между процессами.
